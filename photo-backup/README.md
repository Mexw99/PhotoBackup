# PhotoBackup

แอปจัดการรูปภาพบนเดสก์ท็อปด้วย Wails v2, Go, Nuxt 4 และ SQLite/GORM
รองรับบันทึกโฟลเดอร์ต้นทาง/ปลายทาง ย้ายรูปไปเก็บที่ปลายทาง และใช้ Gemini Flash สร้างคำอธิบายกับ Tag
ค้นหาชื่อไฟล์และคลิก Tag Cloud ได้หลาย Tag โดยแสดงรูปที่มี Tag ใด Tag หนึ่งที่เลือก
เมื่อไม่เลือก Tag และไม่ได้ค้นชื่อไฟล์ จะแสดงรูปทั้งหมด

อ่าน [คู่มือเตรียมตรวจความก้าวหน้าและไล่อ่านโค้ด](docs/PROGRESS_DEMO.md)
สำหรับหัวข้อที่ทำเพิ่ม วิธีสาธิต และไฟล์สำคัญตามเกณฑ์ตรวจรอบนี้

หน้า Tag มีปุ่ม “ลบ” ข้างแต่ละ Tag ใน Tag Cloud เพื่อลบ Tag ออกจาก SQLite
และยกเลิกความสัมพันธ์กับทุกรูป โดยเก็บรูปภาพไว้ตามเดิม
ปุ่ม × บน Tag ของรูปแต่ละรูปยังใช้สำหรับเอา Tag ออกจากรูปนั้นเพียงรูปเดียว

ด้านบนหน้า Tag สรุปสถานะเป็นจำนวน **รูป**: สำเร็จ / กำลังวิเคราะห์ / Retry / รอคิว / ไม่สำเร็จ
แยกจำนวนรูปที่มี Tag (รวมที่เพิ่มเอง) และจำนวนคำ Tag ออกจากจำนวนที่ AI วิเคราะห์สำเร็จ
รูปที่มี Tag อยู่ด้านบน อัปเดตเฉพาะ ID ที่เปลี่ยนครั้งละไม่เกิน 100 รูปโดยไม่ถอดรายการออกจากหน้า
รักษารูปที่กำลังอ่านและการเลือก checkbox ขณะอัปเดต ส่วน Retry รวมเวลารอลองใหม่และการแยกชุดเป็นรายรูป
สถานะ `retrying` เก็บใน SQLite และกลับเข้าคิวเมื่อเปิดแอปใหม่ ไม่ต้องล้างฐานข้อมูล

## เริ่มพัฒนา

ต้องมี Go ตาม `go.mod`, Node.js/npm และ Wails CLI v2
รันคำสั่งจากโฟลเดอร์ `photo-backup`:

```powershell
cd frontend
npm ci
cd ..
wails dev
```

Wails จะเริ่ม Nuxt และสร้าง JavaScript/TypeScript bindings ใน `frontend/wailsjs`
การเปิด Nuxt ในเบราว์เซอร์เพียงอย่างเดียวไม่มี native Go bridge สำหรับเรียกฐานข้อมูลหรือ dialog

หลัง `npm run generate` ใน `frontend` รัน `node tests/tags-scroll.mjs`

ครอบคลุมตำแหน่งเลื่อน การเรียงรูป สถานะ Retry การเลือกภาพ event ระหว่างโหลด และโหลดข้อมูลล้มเหลวแล้วลองใหม่

อ่าน [โครงสร้างและแนวทางเพิ่มไฟล์](docs/PROJECT_STRUCTURE.md)
แผนแบ่งงานเดิมอยู่ใน `docs/planning/`
[คู่มือฐานข้อมูลเดิม](docs/database/DATABASE_GUIDE.html) ใช้อ่านพื้นฐาน GORM และความสัมพันธ์ Tag
เป็นเอกสารเวอร์ชันก่อนหน้า ตัวอย่างการสำรอง การค้นหา และ schema บางส่วนต่างจากรอบนี้
ให้ดูคู่มือ Progress Demo สำหรับพฤติกรรมล่าสุด และดู `model/` กับ `database/database.go` สำหรับ schema ปัจจุบัน

ฐานข้อมูลเก็บที่ `os.UserConfigDir()/PhotoBackup/photo-backup.db` ตามระบบปฏิบัติการ
การสำรองรูปเป็นการ **ย้ายไฟล์จริง** รองรับ JPG, JPEG และ PNG
ระบบเตรียมไฟล์ปลายทางและบันทึก SQLite ให้สำเร็จก่อนลบต้นทาง
เมื่อย้ายสำเร็จ รูปจะอยู่ที่ปลายทางและหายจากโฟลเดอร์ต้นทาง
การเตรียมไฟล์ใช้ worker สูงสุด 4 ตัว ส่วนการบันทึก SQLite ทำทีละรายการเพื่อป้องกัน database lock
หลัง Backup สำเร็จ ระบบส่งรูปเข้าคิว AI แยกต่างหาก ใช้ Worker พร้อมกันได้สูงสุด 8 ตัว
ค่าเริ่มต้น 4 ตัว และส่ง Gemini เป็นชุดละ 5 รูป จึงไม่ทำให้การย้ายไฟล์ต้องรอ API
จำนวน Worker จะไม่เกินจำนวน API Key ที่ตั้งไว้ เพื่อไม่ยิง Key เดียวพร้อมกันจนชน Rate Limit
AI เก็บ `Description`, Tag, สถานะ, error และ hash ของไฟล์ไว้ใน SQLite ถ้าไฟล์เดิมถูกวิเคราะห์แล้วจะใช้ผลเดิม
ชื่อไฟล์ซ้ำในต้นทาง ปลายทาง หรือประวัติ Database (เทียบเฉพาะชื่อ ไม่เทียบเนื้อหา และตรวจข้ามโฟลเดอร์ย่อยโดยไม่สนตัวพิมพ์เล็ก–ใหญ่) จะถูกข้าม ไม่ย้ายและไม่ลบต้นฉบับ หน้า Backup แสดงจำนวนและรายชื่อไฟล์ที่ข้ามพร้อมตำแหน่ง/เหตุผล โดยไม่เขียนทับหรือสร้างไฟล์ `(1)`
มีปุ่มตรวจสอบปลายทางเพื่อค้นหาไฟล์ที่หายหรือขนาดไม่ตรงกับข้อมูลใน Database
ถ้าปลายทางและ DB พร้อมแล้วแต่ลบต้นทางไม่ได้ ระบบรายงานล้มเหลวและเก็บข้อมูลทั้งสองฝั่งไว้

## ตั้งค่า Gemini Flash AI

การ Backup ใช้งานได้แม้ไม่ตั้งค่า AI แต่รูปจะอยู่สถานะ `รอวิเคราะห์`
โปรเจกต์จะโหลดค่าจากไฟล์ `.env` ที่อยู่โฟลเดอร์รากของโปรเจกต์อัตโนมัติก่อนเปิด Wails และใช้ Gemini Flash วิเคราะห์รูป

สร้างไฟล์ `.env` จากไฟล์ตัวอย่าง:

```bash
cp .env.example .env
```

แล้วแก้ค่า `GEMINI_API_KEYS` ในไฟล์ `.env` โดยคั่นคีย์ด้วย comma:

```env
GEMINI_API_KEYS=คีย์ที่1,คีย์ที่2,คีย์ที่3,คีย์ที่4
PHOTO_BACKUP_AI_MODEL=gemini-3.5-flash
```

ระบบจะหมุนใช้คีย์ตามคำขอและ Retry หากต้องการใช้คีย์เดียว ให้ใส่ใน `GEMINI_API_KEY` ได้
ห้ามใส่คีย์จริงใน `.env.example` หรือ commit ไฟล์ `.env` ขึ้น Git

จากนั้นรัน:

```bash
wails dev
```

ไฟล์ `.env` ถูกตั้งให้ Git ไม่ติดตาม ห้าม commit API key ลง Git รูปจะถูกส่งจากไฟล์ปลายทางไปยัง Gemini API
ถ้า Batch ล้มเหลว ระบบจะ Retry ตาม `AI_MAX_RETRIES` แล้วแยกวิเคราะห์ทีละรูปเป็นทางสำรอง
ผลลัพธ์ที่ไม่มี Description หรือ Tag จะไม่ถูกบันทึกเป็นสำเร็จ และจะไม่ปล่อยให้รูปขาด Tag แบบเงียบ ๆ
หน้าแสดงรายการใช้ Thumbnail ขนาดเล็กและรวมการรีเฟรชจาก event เป็นช่วง ๆ เพื่อลดการใช้หน่วยความจำเมื่อมีรูปจำนวนมาก
หลังวิเคราะห์เสร็จ ผลลัพธ์จะถูกเก็บใน SQLite และหน้า Dashboard, Tag และ Search จะอัปเดตผ่าน event
